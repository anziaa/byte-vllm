# int8 prefill tile 修复：把「w8a16 在 prefill 上慢 15%」拆掉 73%

> 复盘记录，对应 TODO 步 7 的 P0 项，数据出处 [`docs/REPORT.md`](../REPORT.md) 12.8 / 12.9，提交 `c73095f`。
>
> **整理说明**：修复本身已在 `nanovllm/layers/int8_linear.py` 的 tile 选择逻辑里；文中引用的扫描脚本（`scripts/scan_tile_threshold.py` 等）在整理时裁掉了。
> 写这份笔记的目的不只是记结论：**这个 bug 的形态（静默降级的流水线）和修它的方法（先扫阈值、再用两套口径闭合）比结论本身更可复用。**

---

## 1. 一句话结论

int8（w8a16）在 prefill 上比 bf16 慢的那 16.2%，**73% 不是量化的固有代价，是 tile 表选错**。改两行、加一个 `M≥256` 分支之后：

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| C=64 的 prefill 段（16384 token） | 621.4 ms | **560.0 ms** |
| int8 prefill 退化率 | 1.15（+16.2%） | **1.042（+4.2%）** |
| C=64 端到端净收益（vs bf16） | +7.3% | **+10.4%** |
| TTFT@2048（int8 vs bf16 80.3） | 87.0 ms（+8.1%） | **80.8 ms（+0.6%）** |
| M=16384 单层 down / o_proj | 3947 / 2711 µs | **2736 / 1812 µs** |

---

## 2. 起因：那 82 ms 是怎么被切成两块

`measure_throughput()` 的墙钟含 prefill，拆开窗口后 C=64 的 16384-token prefill 是「bf16 539.4 ms vs int8 621.4 ms」，赔 82 ms。原来的解释停在「w8a16 只买带宽不买算力」，但这句话解释不了**为什么同一个 kernel 在 decode 上是净赚 12.2%**。

真正的原因在 `_pick_tiles()`：那张 tile 表是 `autotune_w8a16.py` 在 **M=1..64（decode）** 上扫出来的，prefill 原封不动继承了它。而 decode 和 prefill 对 tile 的诉求**正好相反**：

| | decode（M≤64） | prefill（M 大） |
| --- | --- | --- |
| 瓶颈 | 权重带宽（每步要读一遍 0.6 GB） | 算力 / 并行度 |
| program 数 | 不够，要拆细（BN=32 换 32 个 pid_n） | 已经够多，要合并（少发块、少摊固定开销） |
| 片上预算 | 富余 | 紧张，直接决定流水能开几级 |
| 结论 | `BN=32, BK=128` | `BN=64, BK=64` |

---

## 3. 三个数字是什么（顺带把机制讲清）

`_pick_tiles()` 返回 `(BM, BN, BK, num_warps, num_stages)`，前三个是 GEMM 的切块尺寸，**单位是元素个数**：

- `BM`：M 方向（token 方向）每块多少行
- `BN`：N 方向（输出通道方向）每块多少列
- `BK`：K 方向（内积归约方向）每次循环啃多深

一个 program 的计算形态是：读 `x[BM, BK]` → 读 `w[BK, BN]` 并反量化 → `tl.dot` 累进 `acc[BM, BN]`（fp32）→ K 方向循环 `K/BK` 次。

推导出来的两条基本关系：

```
program 总数 = ceil(N/BN) × ceil(M/BM)
smem / 级    = (BM×BK + BK×BN) × 2 字节      # x 是 bf16，w 反量化后也是 bf16
实际流水级数 = min(num_stages, floor(100 KB / smem_per_stage))
```

down 层（K=3072, N=1024）在 M=16384 上，三套配置的账：

| tile | program | smem/级 | 3 级需要 | 实际上限 | 时间 |
| --- | --- | --- | --- | --- | --- |
| `128,32,128`（老表） | 32×128 = 4096 | 32+8 = 40 KB | 120 KB ✗ | **2 级** | 3947 µs |
| `128,64,128`（只改 BN） | 16×128 = 2048 | 32+16 = 48 KB | 144 KB ✗ | **2 级** | 3434 µs |
| `128,64,64`（新表） | 16×128 = 2048 | 16+8 = 24 KB | 72 KB ✓ | **3 级** | 2736 µs |

两笔改动各治一个病，合计闭合成 1211 µs：

- **BN 32→64（−513 µs，42%）**：program 数减半，每块固定开销（prologue/epilogue、index、mask）摊薄；同时激活片总流量按 `pid_n` 成比例减半。
- **BK 128→64（−697 µs，58%）**：与 program 数无关，纯粹是 smem 从超限降到 72 KB，流水从 2 级回到 3 级。

### 3.1 为什么少一级流水会慢 27%

2 级缓冲只有两个，`load(i+1)` 必须在 `calc(i)` 结束前完成，否则下一拍空等：

```
2 级：周期 = max(L, C)          3 级：周期 = max(C, L/2)
```

3 级允许 load 提前两拍发，只要 `L < 2C` 就能完全藏住。而这里的 L 一点不短——每次 load 还要捆着 `int8 → fp32 → ×scale → bf16` 这条反量化 ALU 链。

**自洽校验**：实测 3434/2736 = 1.255。若 `L ≈ 1.26C`，2 级周期 1.26C、3 级周期 C（因为 1.26C < 2C），比值正好 1.26。两个独立观测量落在同一个数上，支持「2 级 → 3 级」这个读法。（这是推断 + 一致性验证，没有抓 profiler 的 stall 计数。）

**这个坑最阴的地方**：`num_stages=3` 照传不误，装不下时 Triton 静默退到 2 级，不报错、不打日志。代码、告警、正确性全看不出异常，**只有计时曲线会说话**。

## 4. 阈值为什么定在 256（不能推，只能扫）

改造方向清楚之后，唯一危险的参数是阈值：BN 翻倍会把 `pid_n` 从 32 砍到 16，小 M 时 program 总数可能连 36 个 SM 都填不满。先验推理给出两个互相矛盾的答案（有人推 256，有人推 512），所以直接扫。

`scripts/scan_tile_threshold.py`：4 个 shape × 8 个 M × 3 个候选，每次 flush L2、取中位。

| M（down） | `128,32,128` | `128,64,64` | 胜者 |
| --- | --- | --- | --- |
| 128 | **55.3 µs** | 77.8 | 老表（+41%） |
| 256 | 99.3 | **79.9** | 新表（−20%，**反转点**） |
| 512 | 179.2 | **123.9** | 新表（−31%） |
| 2048 | 491.7 | **356.4** | 新表（−28%） |
| 16384 | 4048.9 | **2768.9** | 新表（−32%） |

o_proj 同构（M=128：33.8 vs 46.1；M=256：50.2 vs 60.4），转折点同样是 256。

**M=128 那行正好验证了机制**：`pid_n=16 × pid_m=1 = 16` 个 program，36 个 SM 只填得进 16 个，BN 翻倍带来的省固定开销完全被并行度损失吃掉。同一条理由也解释了为什么 M=256（32 个 program < 36）仍然反转——此时 BK 减半换来的 3 级流水已经能补回并行度损失。

还有一个反方向的上限，同样是扫出来的：继续把 program 减半到 1024（`128,128,64` 或 `256,64,64`）在 M=16384 上反而慢 382/432 µs，因为累加器 `128×128` fp32 要 8 warps 才摊得开。

> **方法论**：tile 的一半是 smem 预算的整数规划，另一半是并行度/寄存器的权衡，**没有可以外推的单调趋势**。所以「调 tile」这种活永远是先扫后改，改完再扫一次确认。

## 5. 改动

`src/nanovllm/layers/int8_linear.py::_pick_tiles`：

```python
BM = 16 if M <= 16 else (32 if M <= 32 else (64 if M <= 64 else 128))
if N <= 2048:
    if M >= 256:
        return BM, 64, 64, 4, 3   # prefill：BN×2 摊薄 program，BK÷2 换回 3 级流水
    return BM, 32, 128, 4, 3      # decode / 短 prefill，一个字符没动
if N >= 65536:
    return BM, 128, 32, 4, 2      # lm_head
return BM, 64, 32, 4, 3           # qkv / gate_up
```

影响面严格限定在 `N≤2048`（down、o_proj）且 `M≥256` 的前向。decode 走 `M≤64`，短 prefill 走 128，**12.x 里所有 decode 结论一个字都不用改**。

## 6. 验收：四条判据 + 一次闭合

### 6.1 端到端（`prefill_vs_M.sh`，两轮反序取中位；prompt 256、`max_tokens=1` → dt 即纯 prefill）

| C | M | 修前 bf16 / int8 / Δ / ratio | 修后 bf16 / int8 / Δ / ratio |
| --- | --- | --- | --- |
| 8 | 2048 | 71.2 / 90.2 / +19.0 / 1.27 | 74.8 / 73.6 / **−1.3** / 0.98 |
| 16 | 4096 | 136.1 / 173.4 / +37.3 / 1.27 | 135.8 / 139.7 / **+3.8** / 1.03 |
| 32 | 8192 | 273.3 / 339.2 / +65.8 / 1.24 | 271.4 / 282.0 / **+10.6** / 1.04 |
| 64 | 16384 | 539.4 / 621.4 / +81.9 / 1.15 | 537.4 / 560.0 / **+22.7** / **1.042** |

- C=64 的 Δ 从 +81.9 → +22.7（**−59.2 ms**），预测是 −60 ms。
- bf16 两侧 539.4 → 537.4（−0.4%），**基线没动，不是靠基线漂移挣来的**。
- C=8 那行 bf16 自己从 71.2 漂到 74.8（dt 只有 74 ms），是高噪声档，只当趋势看。

### 6.2 微基准与端到端闭合（最关键的一步）

| shape（M=16384） | 修前 | 修后 | 单层省 | × 28 层 |
| --- | --- | --- | --- | --- |
| down（K=3072 N=1024） | 3946.5 µs | **2736.1** | −1210.4 | −33.9 ms |
| o_proj（K=2048 N=1024） | 2710.5 | **1811.5** | −899.0 | −25.2 ms |
| 合计 | | | −2109.4 | **−59.1 ms** |

**−59.1（微基准，单 kernel）vs −59.2（端到端，28 层整段 prefill）**。两种口径、两套实验、两个数吻合到 0.1 ms，这才算验证成立；单看端到端省了 59 ms 只能说「变快了」，说不出「快在哪」。

## 7. 数值：不是「末位微动」，是逐元素 100% 一致

原先的预期是「换 tile 会改累加顺序 → logits 末位微动 → 需要重跑 ppl」。实测推翻了这个担心。

`scripts/check_tiles_int8.py` 在 M=128/256/512/2048/16384 × {down, o_proj} 上对比新旧 tile 的输出：**rel_L2 全 0.00e+00，逐元素一致率 100%**。

原因（解释，非独立验证）：mma 的硬件 K 粒度是 16，`BK=128` 与 `BK=64` 只是外层循环跑几次的区别，指令级累加顺序完全没变。

**所以这次不用重跑 ppl。** 这比「差多少个百分点以内」强一档——它是位级等价，不存在需要量化的误差。

---

## 8. 边界跟着变了

修前：prefill 每输入 token 净赔 **0.0050 ms**（82 ms / 16384），decode 每输出 token 净赚 0.0339 ms → 判据「输出/输入 token 比 > **0.15**」才净赚。

修后：prefill 每输入 token 净赔 **0.0014 ms**（22.7 / 16384，预测 0.0013）→ 判据放宽到「> **0.04**」。

结论：官方协议（0.94）轻松赚 10%；纯 prefill 批处理从净亏 15% 降到**净亏 4%**。剩下这 4% 是 w8a16 的固有税（反量化 ALU ∝ token 数），换 tile 修不掉——真要 prefill 也快，得换 **w8a8**（走 int8 tensor core，峰值 2×），那是另一条技术路线。

---

## 9. 没做的事（写清边界，免得下次重复评估）

1. **qkv / gate_up（N>2048）没动**：M=16384 上 `128,128,32` 对 gate_up 快 4%（5453 vs 5684 µs），但 4% 落在单流 run-to-run ±4% 里读不出来，且 `128,128` 的累加器要 8 warps 才摊得开，不冒这个险。
2. **decode tile（P3）没碰**：decode 侧只剩 0.4 ms/步（2–3%）的空间，不值得单开实验。
3. **没有做请求级门控**（另一轮讨论的结论）：`prefill_compile` 的收益是带状的（L=768 −25.3 ms，L=2048 +0.9±0.4 ms），按长度硬切会把批误判、一次赔 12 ms，不如用部署级开关 `NANOVLLM_PREFILL_COMPILE=off`。

## 11. 踩过的坑（下次别再踩）

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| Triton 静默降流水 | `num_stages=3` 照传，实际 2 级，无任何告警 | 自己算 `smem/级 × 级数` 对 100 KB 预算；用计时曲线反推级数 |
| 单发 kernel 调 tile | launch 开销淹没信号（一次 20 µs） | 28 份不同权重连发再除 28，每次 flush L2，首尾自校准（漂移 >1.1× 整轮作废） |
| tile 外推 | 128/256/512 三档趋势一致就以为能推 | 只信扫描点；M=128 和 M=256 就是相反结论 |
| `wsl.sh sh` 里写 for 循环 | `--quant \$q` 被两层引号吃掉 → `argument --quant: expected one argument` | 带变量的逻辑写进脚本文件，别塞进 `wsl.sh` 的字符串 |
| 用含 prefill 的吞吐反算 decode 带宽 | 得出「int8 掉 10.4% 带宽」这种假结论 | 拆窗口：`dt(n) − dt(1)` 才是纯 decode（RESULTS 12.3） |
| prefix caching 污染单点 measurement | 同长度墙钟分 27/52/78 ms 三档，像「快 3 倍」 | prefill 单点测量必须 `--prefix-caching 0` |

## 12. 三句话拿走

1. **性能异常的形态比数字更重要**：这次是「静默降级的流水线」，代码和告警都干净，只有计时曲线能看出来。查这类问题要先算资源预算（smem / program / 寄存器），再对时间。
2. **改之前先扫，改之后再扫**：tile 类参数没有单调性，先扫能省一次错误的阈值，后扫能确认改动真的落在预期的量级上。
3. **验证要两个口径闭合**：微基准 −59.1 ms 与端到端 −59.2 ms 吻合，比任何单侧的「变快了」都可信；反过来，只有端到端数字时说不出钱花在哪。
